# RCA — Deploy build_image failure (run 1fd32c20-a0e5-4b31-ac74-60038da6283c)

## Summary
The redeploy of `odisha-learning-pro` (template `nextjs_mongo_shadcn_base_image`) failed at the **build_image** step. This is a **source-level** failure (CODE), not a manifest, infra, or secrets problem. **No secrets/env were touched, and nothing was promoted — the app remains live on the previous good run `301fb2a7-a8b3-41c4-bda6-2695cd7eaa98`.**

## Root cause
During `docker-build` (Cloud Build step #2), the Next.js builder stage runs:
```
RUN if [ -f yarn.lock ]; then yarn --frozen-lockfile --network-timeout 100000; ...
```
and it failed (build log lines 492–497):
```
#16 2.961 error Your lockfile needs to be updated, but yarn was run with `--frozen-lockfile`.
ERROR: executor failed running [/bin/sh -c if [ -f yarn.lock ]; then yarn --frozen-lockfile ...]: exit code: 1
```

`yarn.lock` is out of sync with `package.json` in the deployed source. `package.json` was modified in preview (consistent with this release's new work — the private-R2 write path / store code), but `yarn.lock` was not regenerated to match. Because the production Dockerfile installs with `--frozen-lockfile`, yarn refuses to proceed when the lockfile would need updating, and the build aborts.

## NOT the cause (ruled out)
- The earlier `restore-pip-cache` line `CommandException: No URLs matched: gs://.../pip-cache.tar.gz` is a **benign cache miss**, not the failure. The build proceeded past it to step #2.
- No manifest fault: the `--frozen-lockfile` behavior is the intended, standard template behavior.
- Not a secrets/tier/infra issue.

## Fix (CODE — owned by E1, applied in the preview/source environment)
1. In the app root (where `package.json` and `yarn.lock` live), run `yarn install` to regenerate/update `yarn.lock` so it matches the current `package.json`.
2. Commit the updated `yarn.lock` into the source.
3. Re-trigger the deploy.

Do NOT change any env/secrets. This is purely a lockfile sync.

## Verification note
Eph sandbox could not be brought up (transient `eph_source_check_failed` / "container not found" across 3 retries), so the fix was not reproduced in-pod. Root cause is unambiguous from the Cloud Build log excerpt above (exact yarn `--frozen-lockfile` error). After regenerating `yarn.lock`, the `yarn --frozen-lockfile` install will succeed.
