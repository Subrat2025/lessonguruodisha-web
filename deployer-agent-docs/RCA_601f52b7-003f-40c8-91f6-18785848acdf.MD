## Why the sample could appear blank to users (server render is healthy, so causes are downstream/content-specific)
Ranked, given the server returns valid PNGs:
1. Item-specific content: a particular item's stored HTML renders a blank page-1 (e.g. content paints asynchronously and the page-1 screenshot fires before paint for that template/item). The two items I tested rendered fine; a different itemId may not.
2. Stale/blank cached artifact for a specific item: if a blank PNG was ever cached (during a past transient failure) for a given item key in the R2 private bucket, reads could serve that blank. Not observed for my test items (they re-rendered), but possible per-item.
3. Client-side: stale/blank cached response in the user's browser or CDN edge for the sample URL; needs a hard refresh / incognito to rule out.
4. Cold-start latency: first render on a cold pod takes 8-14s; if the frontend has a shorter client timeout it may show an empty/broken image while the server actually succeeds.

## What is needed to pin the exact blank case
The specific itemId(s) users see blank. With that id I can re-probe the live sample endpoint and confirm whether that item renders blank server-side (content bug) or returns a valid PNG (client/cache issue).

## Bottom line
- Full PDF download path: Chromium is healthy on LIVE; the only gate hit was the expected signed-token check. No render-level failure found.
- Sample preview: healthy on LIVE — returns valid non-blank PNGs. The reported "blank" is not reproducible server-side with the items tested and is most likely item-content-specific or client/cache-side.
