## The real failing step (not the pip-cache line)
The error tail everyone sees quotes `restore-pip-cache: CommandException: No URLs matched: gs://.../pip-cache.tar.gz`. That is a **benign cache miss** (a first/cold build has no cached pip tarball; the `extract-pip-cache` step tolerates it). It is NOT the cause. The terminal failure is:

## Root cause
The `next.config.js` changes described (serverComponentsExternalPackages, `webpack()` IgnorePlugin, server `config.externals`, `runtime='nodejs'`) are **not being applied by the config that Next.js actually loads during the Cloud Build**. If the IgnorePlugin were in effect, the three `Can't resolve nock/mock-aws-s3/aws-sdk` errors would not appear; if `externals`/`serverComponentsExternalPackages` were in effect, `muhammara` and `archiver` would not be traced into the bundle at all. All of them still appear → the fixed config is not in effect in the pulled source.

The local build passes (`NODE_OPTIONS=... yarn build` in ~70s) while the Cloud Build fails with the pre-fix output. The only variable between them is **which source/config the build actually consumes**. The deployer pulls the app directory from the agent-env (preview) pod; the cloud build's `yarn build` is behaving as if the config still has none of the fixes.

Note: I could not reproduce in an eph sandbox — the eph provisioning service was returning 500/504/409 (`pod not running`, `container not found`) on every attempt during this session. This diagnosis is therefore from the Cloud Build logs of two independent runs (7c077539 and the fresh force_repull run 12c75e67), which are conclusive that the config fix is not taking effect — but it was NOT reproduced in-sandbox.

## What E1 must check/fix (source — not deployable by the deployer)
1. **Confirm which config file Next.js actually loads in the DEPLOYED source dir.** Run `ls -la next.config.*` at the repo root of the preview app. If there is BOTH a `next.config.js` and a `next.config.mjs`/`next.config.ts`, Next.js uses only one — the fixes may have landed in the file that is NOT loaded. Consolidate to a single config file that contains the fixes.
2. **Verify the edited `next.config.js` is actually saved in the directory the deployer pulls** (the live preview `/app`), not in a scratch copy / different checkout. The cloud build shows the config having no effect, which most commonly means the deployed copy still holds the old config. Re-open the file in the preview app and confirm the `webpack()` hook + `IgnorePlugin` + `serverComponentsExternalPackages: ['muhammara','archiver','pdf-lib','@pdf-lib/fontkit']` are present and syntactically applied (e.g. the `webpack` function actually `return config`s, and it isn't shadowed by a second exported config).
3. **Confirm the config export shape.** If `next.config.js` exports a function or is wrapped (e.g. by a plugin/`withX()`), make sure the `webpack` hook and `experimental.serverComponentsExternalPackages` survive the wrapping and aren't dropped.
4. After confirming the fixed config is in the deployed source, re-trigger the deploy. A fresh pull+build is the definitive test (that is exactly what `resume_pipeline` does).

## What is NOT the problem
- Not a manifest/Dockerfile issue — the template correctly runs `yarn build`; no manifest override was made or is warranted.
- Not the pip-cache "No URLs matched" line (benign cold-cache miss).
- Not tier/memory — the failure is a webpack compile error, not an OOM.
