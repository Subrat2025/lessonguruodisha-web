## 4) CDN/edge cache in front of /api/*?
- **From the platform: none.** This template serves Next.js straight from Kubernetes; there is no Cloudflare worker / KV / R2 edge layer in front of it (that layer only exists for `fastapi_react_mongo` cloudflare-frontend apps). So the platform adds no stale-GET cache.
- Next.js itself *can* statically pre-render a GET route handler at build time if it is not marked dynamic — that is what `export const dynamic='force-dynamic'` guards against. But this cannot explain the symptom: the owner's decisive evidence is a **POST** (`create-order`), which Next.js never statically caches, and `GET /api/plans` already reflects live DB state (so it is not serving a frozen build snapshot either).
- If the owner has independently placed lessonguruodisha.in behind **their own** Cloudflare with a "cache everything" rule, that could cache GETs — but it still cannot cache the POST, so it is not the cause of the create-order behaviour.

## ROOT CAUSE
Plans are **data in MongoDB**, not constants in the shipped bundle. The admin-customized `settings.plans` document (`customized:true`) is the source of truth the running app serves, and it **still contains the `ambassador-yearly` entry at ₹99**. A code change that strips ambassador from the *hard-coded default* plan list (`AMBASSADOR_PLAN_KILL`) is effectively **dead code against a DB-driven plan list** — it ships, the image is live, but it does not mutate the DB document, so nothing changes on LIVE. `create-order` continuing to mint a ₹99 ambassador order is consistent with its plan lookup resolving `ambassador-yearly` straight from the DB plans array (which still has it at ₹99) rather than honouring `enabled:false` / an active-only filter.

Definitively: (a) the prod build is NOT failing — the latest image is built and live; (b) responses are NOT being cached (no platform CDN; POST is uncacheable; GET already shows live DB). It is (c) — the right image is live, but the plan behaviour is governed by DB data the code edit never touches.

## FIXES
**Fix 1 (data — immediate, stops the ₹99 ambassador orders):** In the PRODUCTION DB (`odisha-learning-pro-edumaster_odisha`), edit the `settings` document `key:"plans"` (`_id 6a327c73aa7b65a70c2ad00a`) and **remove the `ambassador-yearly` object** from the `value` array (leaving it merely `enabled:false` is not enough while create-order resolves it by id). Use Deployment Panel → Database (DB Manager). This takes effect immediately, no redeploy needed, because plans are read from the DB at request time.

**Fix 2 (code — E1 to apply in source, then redeploy):** In `app/api/[[...path]]/route.js`, make `create-order` resolve the plan from the **active/enabled** list (the same filtered output `getActivePlans()` produces) and return **400 "Invalid plan"** for any plan that is disabled or not in the active set — instead of looking it up in the raw DB plans array. Because plans are DB-sourced when `customized:true`, apply the `AMBASSADOR_PLAN_KILL` / enabled-filter to the **DB-derived** list, not only to the hard-coded defaults. (The `export const dynamic='force-dynamic'` edit is fine to keep but is not the cause here.)

**Not reproduced in sandbox:** eph pod boot failed (envcore infra), so the exact current contents of the deployed `route.js` were not read; the root cause stands on the build-artifact + DB evidence above, which does not depend on that inspection.
